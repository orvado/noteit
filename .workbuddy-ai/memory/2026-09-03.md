# 2026-09-03 — Invisible cursor / blank editor pane fix in NoteIt

## Root cause
NSTextView rasterizes its drawn text into an internal CALayer keyed to the
*current* visible rect. When that rect changes — e.g. an NSRulerView makes
NSScrollView reposition the clip view, or the gutter is toggled on/off so the
clip view's width changes — the content layer keeps its old `position` and
`bounds`. The text view is in the right place, the data is correct, focus
works, glyphs are laid out — but the rasterized text sits at the stale
geometry, so the editor pane paints blank.

## Fix (in Sources/NoteIt/EditorView.swift)
- Replaced `NSRulerView` line-number ruler with a sibling `LineNumberGutterView`
  (NSView, flipped, draw-line-numbers-from-layout-manager). Sidesteps the
  scroll-view clip geometry mangling entirely.
- Added an `EditorContainerView` that owns the gutter + NSScrollView and
  arranges them in `layout()`.
- Final piece: in `EditorContainerView.layout()`, after any geometry change,
  "jiggle" the text view's frame size (`setFrameSize(h+1)` then `setFrameSize(h)`)
  so NSTextView's content layer invalidates and redraws. Without this, toggling
  the gutter hides/shows still left the pane blank even though no ruler was
  involved.

## Verification (since cleaned up)
- Wrote a temp `__Verify.swift` harness with a screenshot hook driven from
  `NoteItApp.onAppear` via `VerifyStore.shared`.
- 6 screenshots: wrap-on/lines-on, typed caret, scrolled-bottom gutter follows,
  wrap-off (with long line to confirm horizontal scroll), lines-off, lines-back-on.
- Deep dump revealed the stale contentLayer geometry (e.g. bounds=900x355 when
  clip view was actually 869 wide).
- Removed all temp code and rebuilt clean.

## SwiftUI click-testing pattern (reusable)
To simulate a SwiftUI `Button` click from a verification harness:
1. Walk `NSApp.keyWindow.contentView.subviews` and find the `_FocusRingView`
   matching the button's geometry (SwiftUI image buttons render as `_FocusRingView`).
2. Compute the centre: `view.convert(NSPoint(midX, midY), to: nil)` — this is
   window-base coords.
3. Build `NSEvent.mouseEvent(.leftMouseDown/.leftMouseUp, location: windowPt, ...)`.
4. Dispatch via `NSApp.sendEvent(_:)`, not `win.sendEvent(_:)` — SwiftUI's
   responder chain routes through the application.

## Snippets manager rework (Sources/NoteIt/Panels.swift)
`SnippetsSheet` was a single flat list where the only actions were "Insert" and
a right-click-only "Delete"; there was no way to edit a snippet at all. Rebuilt
as a master/detail window (720x520):

- Left pane: `List(filtered, selection:)` + filter field + `+ / − / duplicate`
  icon buttons. Row shows trigger (mono) + description, with a warning badge
  when the snippet fails validation.
- Right pane: edits the selected snippet in place via
  `$store.snippets[idx].trigger/.description/.expansion`, plus a live
  `resolvedExpansion()` preview.
- Delete: `−` button, Delete key (`.onDeleteCommand`), and a row context menu —
  all routed through one `pendingDelete` confirmation alert. Deleting reselects
  the neighbour so selection never dangles.
- Validation (`validation(for:)`): empty trigger, whitespace in trigger,
  duplicate trigger, empty expansion. Flagged rows disable "Insert".
- `uniqueTrigger(from:)` appends 2, 3, … so add/duplicate never collide.
- "Restore Defaults" replaces the whole list (confirmation alert).

### Gotchas learned
- **Do NOT "fix" the selection on filter change.** I tried adding
  `onChange(of: filter) { selection = filtered.first?.id }` to silence the
  `reentrant operation in its NSTableView delegate` warning. It did NOT silence
  it, and it introduced a real regression: typing a filter stole the selection,
  so a later delete removed the filtered row instead of the user's snippet.
  Reverted. The warning is a benign one-shot AppKit log during rapid filter
  typing (only reproduced under the synthetic-key harness); leave it alone.
- Verification harness pattern: temp `Sources/NoteIt/__Verify.swift` + a
  `VerifyStore.shared = store` / `Verify.run()` hook in `NoteItApp.onAppear`,
  driven by posting `.noteItSnippets` to open the sheet, then synthesizing
  clicks/keystrokes and logging to stderr. **Delete the harness and revert the
  NoteItApp hook before shipping** (confirmed clean via `strings` on the binary).
- `timeout` is not on macOS. Use a PID watchdog loop instead:
  `( bin > log 2>&1 & echo $! > pid ); for i in $(seq 1 60); do kill -0 $(cat pid) || break; sleep 1; done`.
- `swift build -c release` fails under the agent sandbox
  (`sandbox-exec: sandbox_apply: Operation not permitted`,
  needs `~/.swiftpm/security` write). Re-run with sandbox escalation.
- Footer/icon buttons in SwiftUI render as `_FocusRingView`, not `NSButton` —
  click them by geometry, `NSButton.performClick` won't find them.

### Persistence: verified correct — do NOT "fix" the sink
`$snippets.sink { saveSnippets($0) }` in `DocumentStore.init` looks like the
classic `@Published`-emits-old-value bug. **It is not.** Tested empirically
(`/tmp/pubtest.swift`): `@Published` emits in `willSet`, but the *emitted* value
is the NEW one — only the property still reads old *at emission time*. So
`sink { save($0) }` saves the correct post-mutation array. End-to-end confirmed
with a temp `__Persist.swift` probe: edit + delete appear in UserDefaults
immediately, and survive relaunch (`PT_MARKER` loaded back from disk).
Rule: before "fixing" a persisted-value sink, test the semantics — saving the
emitted value is right, reading `self.snippets` inside the closure would be the
actual bug (it would read the stale pre-mutation value).

### UserDefaults domain gotcha when testing
The debug binary (no bundle) uses suite **"NoteIt"** (process name) →
`~/Library/Preferences/NoteIt.plist`. The bundled app uses its
`CFBundleIdentifier` (**com.noteit.app**) → `com.noteit.app.plist`. These are
*different* domains, so probe/test data written by a debug run does NOT touch
the real app's stored state. Still clean up after probing:
`defaults delete NoteIt "NoteIt.snippets.v1"`.

## Tab close button hit area (ContentView.swift `TabChip`)
The X was `Image(systemName: "xmark").font(.caption2)` — an ~8pt glyph, and
SwiftUI hit-tests only the drawn image, so it was a fiddly target. Fixed by
padding the *target* without growing the *glyph*:

```swift
Image(systemName: "xmark").font(.caption2)
    .frame(width: 18, height: 18)
    .background(RoundedRectangle(cornerRadius: 4).fill(hoveringClose ? .primary.opacity(0.12) : .clear))
    .contentShape(Rectangle())   // <-- essential
```

`.contentShape(Rectangle())` is the part that matters: without it SwiftUI still
hit-tests only the glyph even inside a larger frame. 18pt matches the chip's
text line height, so the tab bar grows ~1pt. `.onHover` adds a subtle highlight
so the enlarged target is discoverable.

### Snippet placeholders (`<#name#>`) are NOT implemented
The tokens appear **only** in the two default snippet definitions in
Models.swift. Nothing parses or navigates them — no `placeholder` handling
anywhere in the codebase. `DocumentStore.expandTriggerIfNeeded` inserts
`resolvedExpansion()` verbatim and leaves the caret at the end, so inserting
the `swiftfunc` snippet leaves literal `<#name#>` text sitting in the document
(one of the autosaved drafts literally contains `let <#name#> = <#value#>`).
`NoteTextView.keyDown` handles Tab *only* to call `expandTrigger`. **There is
no keyboard shortcut for placeholder navigation.**

### SwiftUI view-probe / hit-testing notes
- `.buttonStyle(.plain)` icon buttons render as `_FocusRingView`. Toolbar icon
  buttons are `FocusRingNSButton` 16x16; the tab close is `_FocusRingView`
  18x18 — discriminate by exact size, not just "<= 24".
- Views inside a SwiftUI container report frames **relative to their own
  container**, so identical chips all report the same frame. Always convert
  with `v.convert(v.bounds, to: contentView)` before comparing or ordering.
- SwiftUI `Text` does NOT produce an `NSTextField`, so you cannot find tab
  titles that way — click by converted coordinate instead.
- To *prove* a hit area grew, click at an offset inside the new target but
  outside the old glyph (+7pt from centre of an 18pt target w/ ~8pt glyph).
